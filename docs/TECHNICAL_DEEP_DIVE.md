# DRISHTI — Technical Deep Dive

*A single document covering what was built, which models and features were used, which
datasets and why, how every measure was measured, and what the measurements said —
including where they said the idea did not work.*

**Provenance rule for this document:** every number here is traced to a file in this
repository. Metrics come from `docs/ML_RESULTS.md` (generated by
`scripts/train_and_report.py`, never typed by hand), `STATUS.md` (measured entries with
commit shas), `docs/FUSION_DERIVATION.md`, and `data/measurements/*.json`. Nothing is
carried over from the ideation deck. Where something is designed but unproven, it is
labelled so in-place rather than in a footnote.

Baseline for everything below: **1,232 contract+unit tests + 15 e2e passing**, measured
2026-08-26 at `20a76cf`.

---

## 1. What the system is

DRISHTI is a **defensive** Android malware triage pipeline. It takes a suspicious APK and
returns three things:

1. a calibrated 0–100 threat score `S` with an explicit confidence `C`,
2. a human-readable investigation report in which every AI-written sentence cites a
   concrete artefact, and
3. a hash-chained, Ed25519-signed evidence ledger that a third party can verify.

Its differentiating claim is that the sandbox is **active**: an LLM reads the sample's
environment probes and synthesises the victim environment the sample is looking for
(fake installed banking packages, fake build props, fake locale) until a dormant payload
fires. Samples are real, the corpus is real, and detonation happens on a sealed GCE VM
under nested virtualisation — never on a laptop.

Three engineering commitments shape almost every design decision in the codebase:

- **The LLM never emits the score.** It emits enumerated booleans; Python computes the
  behavioural term from a weight table. An injected `threat_score=0` in a sample's string
  constants is just an unknown dictionary key.
- **The scorer is pure.** `m6_score/engine.py` does no I/O, has no clock, no randomness.
  Same ledger → same score, pinned by a determinism test.
- **Ungrounded claims are rejected inside the write transaction.** `ledger.append()`
  refuses an `AI_CLAIM` whose `evidence_refs` are empty or unresolvable. That rejection
  *is* the product; the refusals leave no gap in the sequence numbers.

## 2. Architecture

Seven modules around one append-only ledger. The critical invariant: **M6 never reads
M2/M3/M4/M5 directly — it reads the ledger.** That is what makes "every score point
traces to an artefact" true rather than marketing.

```
upload/URL ──► M1 INGEST (sha256 · split-merge · dedupe · threat intel)
                     │
        ┌────────────▼─────────────────────────────────┐
        │   EVIDENCE LEDGER (SQLite, append-only,      │
        │   hash-chained, Ed25519-signed)              │
        └──▲──────────▲──────────▲───────────▲─────────┘
           │          │          │           │
     M2 STATIC   M3 SANDBOX   M4 GENAI     M5 ML
     androguard  frida        controller   xgboost + isotonic
     callgraph   emulator     agents+RAG   IsolationForest
     certs/perms TraceSource  Verifier     SHAP
           │          │          │           │
           │     P5 FRONTIER (morph plan · generative C2)
           │          │          │           │
           └──────────┴────┬─────┴───────────┘
                           ▼
              M6 COMPOSITE SCORER  S = f(R, F_AI, G, D),  C = γ(1 − |P_cal − B|)
                           ▼
              M7 REPORT · YARA · STIX · dossier   +   React dashboard
```

**Contracts before code.** Every cross-module type is a pydantic model in
`drishti/contracts/` (37 models at T0.3). No raw dict crosses a module boundary. Adding a
field means editing `docs/01_DATA_CONTRACTS.md` first, then the model, then the code.

**Every module degrades.** External calls (LLM, adb, frida, mitmproxy, gcloud, GCS) are
wrapped so a failing sub-analyser returns a partial result with `errors` populated and an
ERROR node in the ledger, instead of failing the job.

**Pipeline stages** live in exactly one place, `drishti/pipeline.py`:
`INGEST → STATIC → ML → GENAI_STATIC → SCORE_PRELIM → SANDBOX_1 → (FRONTIER) →
SANDBOX_2 → GENAI_FULL → SCORE_FINAL → REPORT`, one ledger node per executed stage.

## 3. M1 — Ingest

sha256 identity, split-APK reassembly (androguard + zip), dedupe against prior jobs, and
an optional threat-intel lookup that feeds the `R` term.

One deliberate refusal here: `reputation.py` **rejects a label-derived intel feed by
default** (`allow_label_derived=False`). AndroZoo's malware label is a threshold on
VirusTotal detections, so feeding a VT-derived signal into `R` would make every
composite metric circular. In the shipped evaluation configuration `R = 0` for exactly
this reason, and it is reported as *ungrounded — not measured*, not as a zero.

## 4. M2 — Static engine

Androguard 4.x in-process, not MobSF. MobSF's Docker image is 3 GB+, its REST schema is
unstable, and androguard gives the XREF call graph for free. The static path parses an
APK **as data** — it never invokes adb, starts an emulator, or executes application code,
so it is the one real-sample path that is laptop-safe. Wall-clock budget: **≤ 90 s**,
enforced with a partial return.

### 4.1 What it extracts

| Group | Content |
|---|---|
| Manifest | permissions, components (activity/service/receiver/provider), exported-unprotected set, deep-link schemes, min/target SDK |
| Certificate | signer, validity window, debug cert, brand mismatch, known-bad reuse |
| Archive | DEX count, mean entropy, native libs, packer hints |
| Strings | URLs, package-name literals, crypto constants (`AES/CBC/…` shaped) |
| Sinks | which dangerous APIs appear, and whether they are *reachable* |
| Rules | permission-combination matches (severity + MITRE) |

### 4.2 The sink taxonomy — `m2_static/sinks.py`

The phase file calls this "the most valuable file here", and it earns it. Each sink
carries three load-bearing fields:

- **`marker`** — a *fragment* of a method signature (`SmsManager;->sendTextMessage`),
  not a full descriptor, because obfuscators rewrite parameter types far more often than
  they rewrite framework class names.
- **`mitre`** — flows into the technique mapper and the STIX export.
- **`severity`** — feeds the `G` term and orders what the LLM is asked about first,
  since prompt budget is finite.

Categories: environment probes (`getPackageInfo`, `getInstalledPackages`,
`resolveActivity` → T1418), dynamic code loading (`DexClassLoader`, `PathClassLoader`,
`System.loadLibrary`, `Method.invoke` → T1407/T1406), exfiltration channels
(`HttpURLConnection`, raw `Socket` → T1437/T1095), SMS, overlay, accessibility,
clipboard, and command execution. The file is observational — it enumerates APIs to
*watch for*; adding a sink widens detection, never capability.

### 4.3 Permission combinations — deterministic rules that feed `G`

`m2_static/rules/permission_combos.yaml`. The signal is the *combination*, not the
permission:

| Rule | Condition | Severity | MITRE |
|---|---|---|---|
| `OTP_THEFT_SURFACE` | `RECEIVE_SMS` ∧ `READ_SMS` | high | T1582 |
| `OVERLAY_CREDENTIAL_THEFT` | `SYSTEM_ALERT_WINDOW` ∧ `INTERNET` ∧ a service | high | T1056 |
| `ACCESSIBILITY_ABUSE` | service bound to `BIND_ACCESSIBILITY_SERVICE` | critical | T1417 |
| `SILENT_SMS_FRAUD` | `SEND_SMS` | critical | T1582 |
| `DROPPER_CAPABILITY` | `REQUEST_INSTALL_PACKAGES` | high | T1407 |
| `SPYWARE_HARVEST` | `READ_CONTACTS` ∧ `READ_CALL_LOG` ∧ `INTERNET` | high | T1412 |
| `NOTIFICATION_LISTENER`, `ANTI_UNINSTALL_PERSISTENCE`, `CAMERA_MIC_SURVEILLANCE`, `LOCATION_TRACKING`, `PERSISTENT_BOOT`, `EXTERNAL_STORAGE_EXFIL` | … | … | … |

The **worst** match wins rather than the sum — five MEDIUM combos are not more damning
than one CRITICAL one, and summing would let volume outvote severity.

This is also why `G` stopped being dead. `G` was specified around YARA family rules,
which do not exist yet, so no caller ever supplied it and it contributed nothing of its
0.15 weight — capping static-only triage at `S = 54`, making HIGH (65) unreachable
without ML or a detonation. A permission combination is the same *category* of evidence
as a YARA hit — a deterministic human-written rule matched, no model in the path — so it
now feeds `G`, raising the static+ML ceiling to **69**.

### 4.4 Call graph — backward BFS from sinks

`m2_static/callgraph.py`, ~50 lines, `networkx` DiGraph over androguard's XREFs.

The question is never "does this API appear" but **"can this API be reached from a
lifecycle entrypoint?"** A `sendTextMessage` reachable only from dead library code is
much weaker evidence than one reachable from `onReceive` of a registered SMS receiver.

Implementation: breadth-first **backwards** from the sink, bounded `max_depth=6`,
`max_paths=5`, callers iterated in sorted order so the traversal is deterministic, with a
`seen_depth` map that prunes any revisit at a worse depth. Output is a `CallPath`
carrying the entrypoint, its kind, the full chain, and `reachable_from_lifecycle`.

That flag becomes the `reach:*` feature family in §5 and the ranking substrate for RAG in
§6.

### 4.5 Bounded decompilation

DAD decompilation is restricted to methods sitting on reachable sink paths — never the
whole APK. This is what makes the RAG workspace in §6.2 possible and bounded.

### 4.6 Lookalike detection — and its honest negative result

`m2_static/lookalike.py` (340 lines) checks whether a sample carries the shape of a
banking trojan: a roster of targeted financial packages in its strings, certificate
posture, and four call-graph reachability signals.

**It was measured and it does not discriminate.** Over **n = 75** real corpus APKs
(35 MalwareBazaar family-tagged banking trojans — Cerberus, Octo, TeaBot, Coper, Hydra,
Ermac, Hook, Alien, BankBot, Joker, SpyNote — against 40 benign;
`data/measurements/lookalike_validation_n75.json`):

- mean `trojan_score` **0.050** malware (max 0.312) vs **0.009** benign (max 0.125)
- rank-AUC **0.621** — weak ordering, well short of usable
- **TROJAN_SHAPE verdicts: 0 benign and 0 malware.** Zero false positives, and zero true
  positives.

The structural root cause is worth stating because it is itself a finding: the four
call-graph reachability signals carry 0.85 of the 1.60 total weight, so the maximum score
reachable *without* them is 0.75/1.60 = **0.4688 < 0.50**, the threshold. Those signals
almost never fire because these recent trojans are **packed** — androguard recovered a
*median of 12 decompiled methods* per sample. The behaviour the discriminator keys on is
not present in the static image at all; it is exactly what M3 detonation exists to
observe.

The threshold and weights were **not** tuned to manufacture a gap. It is retained as an
explanatory UI overlay and **is not a scoring signal**. The panel that does survive is
narrower and deterministic: the decoy's financial roster really does contain
`com.sbi.lotusintouch`, `com.phonepe.app` and `net.one97.paytm`, which gives an
"impersonating SBI"-style line real backing.

## 5. M5 — The machine-learning layer

### 5.1 Datasets — what, why, and what was thrown away

| Source | Role | Why |
|---|---|---|
| **AndroZoo** | volume; older bands | The only source large enough to build a time-split corpus. Labels are thresholded `vt_detection` (`MALWARE_MIN_VT = 10`). |
| **MalwareBazaar** | recent (2024–25) Android tags, family-tagged | Makes the time split *honest*. AndroZoo's recent Android coverage is thin — v1's list had 62 rows from 2024 and 55 from 2025 out of 6,000. |
| **F-Droid / APKPure** | benign baseline | A benign class that is contemporary rather than 2014-era. |

APKs are pulled to `gs://cybershield-505518-corpus/`, extracted on the GCE VM, stored
zipped with the `infected` convention at rest, and never copied to a laptop or committed.

Three corpus-construction decisions, each of which exists because the naive version
silently breaks the evaluation:

1. **A plausibility window on `dex_date`.** `MIN_PLAUSIBLE_DATE = 2008-09-23` (Android
   1.0), `MAX_PLAUSIBLE_DATE = 2026-12-31`. A large fraction of AndroZoo rows carry a
   ZIP-epoch fallback (1980/1981) or impossible futures (2039, 2081, 2092, 2107).
   Unfiltered, they all land on one side of the split — v1's list had 1,235 rows (20.6%)
   dated 1980/81 **all in train** and 23 rows dated 2039–2107 **all in test**, and the
   generalisation claim silently stopped holding. `build_sample_list.py` enforces the
   window and reports how many rows it dropped.
2. **Deterministic interleaving by (split, label)** before extraction. A bucket-ordered
   list means the first N thousand rows are nearly all malware with zero test rows, and
   time-split evaluation cannot run at all.
3. **Evaluation splits extracted first.** The full 10,599-row list would not finish
   inside the deadline, so the prefix that *does* finish was chosen deliberately: test
   and calib complete before any training row, because CI width is driven by test `n`
   while 131 features are learnable from a modest training sample.

Extraction throughput was measured, not guessed: CPU-bound in androguard at ~95% of a
core per shard while the NIC moves 1 MB/s. 4 shards on 8 vCPU → 440 rec/hr; 14 shards on
16 vCPU → 1,489 rec/hr. Memory is the real ceiling and it counts **threads** —
`AnalyzeAPK` holds the DEX and its call graph per thread, so 14 shards × 4 threads put a
64 GB VM into sustained memory pressure and made it unreachable for ~20 minutes.
Fixed with per-unit `MemoryHigh=2500M` / `MemoryMax=3500M` and `Restart=on-failure`;
settled at 14 × 3.

### 5.2 Splits

Time split on `dex_date`. Train = everything older; calib = 2024; test = 2025+.
Three-way, because calibrating on test is a leak.

| split | n | malware | benign |
|---|---:|---:|---:|
| train | 849 | 468 | 381 |
| calib | 207 | 122 | 85 |
| test | 481 | 250 | 231 |

Train bands `['<=2017', '2018-2020', '2021-2023']` are disjoint from test's `['2024-2026']`.
A random split (n=307, 168 malware) is reported alongside, as the contrast.

The calib/test boundary was **re-cut once**, and the re-cut is disclosed in the generated
doc: the shipped calibration split held 5 malware rows, under the 10 needed to fit a
calibrator, so held-out rows were re-partitioned by sha256 bucket (< 3 of 10 → calib),
applied to the held-out bands only, label-independent, train untouched. 180 rows moved
test→calib, 69 calib→test. Assignment by hash bucket rather than by label, because
assigning by label would have manufactured whatever balance flattered the numbers.

Corpus: 1,564 rows, **1,537 usable**; 27 dropped for failed extraction. A sample
androguard cannot parse is **dropped, never zero-filled** — a row of zeros would teach the
model that unparseable looks harmless.

### 5.3 Features — one extractor, 428 columns

`m5_ml/features.py`, schema `1.2.0`. **There is no second code path**: training calls
`extract()` over `StaticReport`s produced by running real M2 on the corpus, inference
calls it on the live `StaticReport`, and `tests/contract/test_feature_parity.py` asserts
both. This is the structural defence against train/inference feature skew, rated the
highest-probability fatal risk in the roadmap.

Features are emitted as a **named sparse mapping**, then projected onto a frozen
vocabulary. The naming is not tidiness — it is why SHAP renders `perm:READ_SMS` instead
of `f_0142`, which is what makes the explainability panel worth showing.

| family | examples | why |
|---|---|---|
| `perm:*` | `perm:READ_SMS`, `perm:count` | Drebin-style baseline |
| `combo:*` | `combo:DROPPER_CAPABILITY`, `combo:count` | the combination is the signal |
| `component:*` | log-counts per kind, `exported_unprotected`, `exported_ratio` | attack surface |
| `intent:*` | deep-link schemes, `has_custom_scheme` | exported-component entry points |
| `sink:*` | one per matched sink, `sink:count` | "this code exists" |
| `reach:*` | per reachable sink, `reach:count`, `reach:min_depth` | **"this code runs"** — dead library code must not score like live code |
| `api:*` | 24 suspicious API tokens, `reflection_count`, `crypto_constant_count` | human-readable and citable in the report |
| `url:*` | counts, distinct hosts, unknown-host count, IP literal, shortener | **counts and flags only, never the URL string** — a URL in a feature name would put attacker-controlled text through SHAP into the report |
| `archive:*` | entropy mean, dex count, multi-dex, native libs, packer hints | packing / obfuscation |
| `cert:*` | validity days, >20y, brand mismatch, known-bad reuse, debug | deliberately **not** "self-signed": every Android APK is |
| `drift:*` | declared-not-used, used-not-declared, over-privilege ratio | static half of `D` |
| `manifest:*` | min/target SDK, gap, legacy export semantics (<31), very old min SDK | manifest hygiene |

Two subtleties that cost real debugging time and are now enforced by tests:

- **`cert:validity_days` is time-invariant by construction.** The analyst-facing
  `age_days` is measured from `not_before` to *now* — the right question for triage and
  the wrong thing in a feature vector, because the same APK yields a different value
  tomorrow. That silently breaks parity and leaks wall-clock time into a time-split
  evaluation. `cert:age_days` and `cert:is_fresh` are **retired** and no longer emitted.
- **`assert_no_retired_features`** refuses a vocabulary that lists a name the current
  extractor cannot emit. This failure is silent by construction: `project()` zero-fills a
  missing feature, so a stale vocabulary still yields a full-width vector with a real
  weight applied to a permanent zero, and nothing raises.

### 5.4 Two leaks that were caught, and how

**`vt_detection` can never become a feature.** AndroZoo's label *is* thresholded
`vt_detection`, so a VT-derived input would make every metric circular.
`dataset.assert_no_label_leak` refuses such a vocabulary outright.

**The two-epoch schema leak.** Extraction ran for days and the extractor was fixed
mid-batch, so the corpus was written by two schema versions: 859 rows at `1.1.0`
(67% malware) and 678 at `1.2.0` (38% malware). Freezing a vocabulary naively puts all
four certificate features in the matrix and zero-fills whichever half is missing —
which encodes *when the row was extracted*, a direct proxy for the label. Same class of
circularity as `vt_detection`, through a different door.

It was found by a measurement (`dataset.epoch_divergent_features`, which computes
per-epoch presence rates) and then **fixed at the root rather than guarded**:
`scripts/reextract_schema.py` re-extracted all 859 stale rows from the **retained** corpus
APKs in GCS — never re-hitting AndroZoo — in two passes (631 at a 20 MB cap, 228 at
70 MB). Final tally: 0 missing, 0 skipped, 0 analysis failures, 0 rows still carrying
`cert:age_days`, 0 missing `cert:validity_days`. The guard now re-runs on every training
run and reports **schema 1.2.0 only, n=1,537, divergent columns NONE**.

### 5.5 Models compared

Five models, identical features, identical splits, seed `20260826`. The only variable is
the model.

| model | specification |
|---|---|
| `logreg_l2` | Logistic regression, L2, C=1.0, balanced class weight, standardised inputs |
| `linear_svm` | LinearSVC (squared hinge, C=0.5, balanced) + 5-fold Platt inside train |
| `random_forest` | 400 trees, `balanced_subsample`, `min_samples_leaf=2` |
| **`xgboost`** | hist, 400 rounds, depth 6, lr 0.06, `scale_pos_weight = neg/pos` |
| `mlp` | (128, 64), ReLU, adam, early stopping on a 10% internal validation slice |

The GNN + sequence transformer + opcode CNN from the ideation paper were **cut**: three
model families that could not be trained, tuned or defended in 72 hours. One
well-calibrated model beats four bad ones.

**Primary metric is PR-AUC, not accuracy or ROC-AUC**, because triage is a ranking problem
on an imbalanced queue. Reported alongside: `FPR@90%R` — the false-positive rate at the
lowest threshold that still reaches 90% recall, which is the actual triage-desk question
("if we insist on catching nine in ten, how much clean traffic does an analyst wade
through?"). All intervals are 2000-resample percentile bootstraps.

| model | random PR-AUC | **time PR-AUC** | gap | 5-fold CV in train |
|---|---:|---:|---:|---|
| `logreg_l2` | 0.9823 | 0.9071 | +0.0752 | 0.9662 ± 0.0239 |
| `linear_svm` | 0.9797 | 0.8834 | +0.0963 | 0.9547 ± 0.0379 |
| `random_forest` | 0.9858 | 0.8962 | +0.0896 | 0.9828 ± 0.0074 |
| **`xgboost`** | **0.9889** | **0.9169** | **+0.0720** | **0.9829 ± 0.0061** |
| `mlp` | 0.9820 | 0.8268 | +0.1552 | 0.9744 ± 0.0125 |

`xgboost` time-split detail: PR-AUC 0.9169 [0.8828, 0.9462], ROC-AUC 0.9131, P 0.8841,
R 0.8240, F1 0.8530, TP 206 / FP 27 / TN 204 / FN 44, FPR@90%R 0.3680.

**Selection never touched the test set.** The winner is the highest 5-fold CV PR-AUC
*inside train*. Picking the best of five by test PR-AUC would turn the test set into a
validation set, and every number afterwards would be the best of five draws rather than
an estimate of field performance.

**The random-vs-time gap is the finding, not an embarrassment.** A random split lets a
model see 2024 malware families while being tested on their siblings; a time split does
not. The ~0.07–0.16 gap is the measured cost of concept drift on this corpus — and the
argument for the behavioural and GenAI layers that do not depend on having seen the
family before. Note also that the two splits have different prevalences (0.547 vs 0.520),
so each PR-AUC must be read against its own no-skill baseline.

Shipped bundle: **`xgboost-428f-1.2.0`**, operating threshold **0.046556** (max-F1 on
calib, n=207 — chosen on calib, never informed by test).

### 5.6 Calibration

Fitted on the held-out calib split (n=207, 122 malware), never on test. 122 positives
clears the isotonic floor, so **isotonic** over Platt — and the *method* is chosen by
cross-validated Brier **within** calib, because choosing it by test Brier is the same leak
one level of indirection away.

| | Brier on test | ECE on test |
|---|---:|---:|
| **isotonic** | **0.113865** | **0.036796** |
| sigmoid | 0.129924 | 0.103692 |
| uncalibrated | 0.186285 | 0.223894 |

ECE improves **−83.6%**. The acceptance criterion a reader can check by hand is the
bucket check: of the 49 test samples scored 0.75–0.85, **79.6%** were malware against an
expected 80% — inside the ±10% tolerance, and the closest that check has come to its
nominal rate. (Before recalibration it was 100% of 9 samples: outside tolerance and, at
n=9, uninformative.) A model can pass every ranking metric and still fail this, and when
it does an entire band of verdicts lands in the wrong bucket.

### 5.7 Novelty escalator — shipped, and measured as not working

`IsolationForest`, 200 trees, fitted on **381 benign training rows only** — fitting on a
mixed corpus would teach it that malware is normal. The published score is a percentile
against that benign distribution, so the threshold means the same thing across retrains.
Escalates at 0.85.

| | value |
|---|---:|
| malware escalation rate | 0.3560 |
| benign escalation rate | **0.3983** |
| lift | **−0.0423** — it fires slightly *more* on clean apps |
| LOW→HIGH promotions | 93, of which **84 benign**, 9 malware |

It is reported rather than tuned until it looks good. A novelty flag fitted on 381 benign
rows measures how unusual a sample is against a *small and narrow* notion of normal, and
on this corpus that is not the same question as whether it is malicious.

It also caused a real product defect, found by measuring the shipped model rather than by
reading the code: it promoted LOW straight to **HIGH**, and HIGH is in `_BLOCK_BANDS`,
which the consumer screen renders as **DO NOT INSTALL**. So a signal intended to mean "a
human should look at this" was issuing an accusation — on 84 benign apps. Fixed to
promote **LOW → MEDIUM** (which maps to REVIEW), with two tests pinning it: the escalator
can never reach a block band, and can never demote a verdict that earned HIGH on real
evidence. It never moves `S` in either case. **The detector is not vindicated by that
fix** — escalating to REVIEW bounds the damage, it does not make the signal good.

### 5.8 Explainability

- **Global:** permutation importance on PR-AUC over the test split (5 repeats,
  shortlisted to the 60 highest-ranked of 428 columns). Model-agnostic and measured,
  rather than read off internal weights. Top: `api:reflection_count` (0.0547),
  `url:count` (0.0154), `perm:READ_SMS` (0.0131), `manifest:target_sdk` (0.0067),
  `combo:DROPPER_CAPABILITY` (0.0049), `sink:network_socket` (0.0042).
- **Per-sample:** `shap.TreeExplainer`, rendered in the report and the UI panel with real
  feature names.

### 5.9 Two measurements that answer "was this worth it"

**Did more data help?** The winner was refit on stratified nested subsamples of train with
test held fixed:

| training n | malware | time-split PR-AUC |
|---:|---:|---:|
| 106 | 58 | 0.8285 |
| 212 | 117 | 0.8433 |
| 424 | 234 | 0.9005 |
| 637 | 351 | 0.9089 |
| 849 | 468 | 0.9093 |

106 → 849 rows bought +0.0808, but the last step (637 → 849) bought **+0.0004**. The curve
has essentially flattened on this corpus — the argument for *widening* the corpus rather
than deepening it.

**Are the certificate features worth anything?** Refit with and without the group on
identical rows and one seed, difference bootstrapped as a **paired** quantity on the same
test split: time-split PR-AUC **0.9169 with, 0.9085 without → +0.0085, 95% [0.0033,
0.0139]**. The interval excludes zero, so the group carries measurable signal — a small
effect. Per-column permutation says the whole of it is `cert:validity_days` (0.0103);
`cert:brand_mismatch` and `cert:known_bad_reuse` are **constant across all 849 training
rows** and cannot carry anything. The defensible claim is "certificate *validity period*
contributes a little", not "the certificate features work".

## 6. M4 — The GenAI layer

### 6.1 Provider, budgets, and what is enforced

Provider is pluggable (`groq` default, `gemini`, and an OpenRouter path verified live).
Budgets are **asserts, not hopes**:

| Resource | Budget | Enforced |
|---|---|---|
| Prompt tokens in | ≤ 12,000 | `client.py` truncates + raises |
| LLM calls per APK | ≤ 25 | `controller.py` counter, hard stop |
| Tool calls per RE session | ≤ 8 | `AnalysisToolbox` |
| Tool result size | ≤ 2,000 chars | truncated with a flag |
| Static wall time | ≤ 90 s | partial return |

Every call is cached by `sha256(model + prompt)` into `.cache/llm/`, with a `--no-cache`
flag for honesty during judging. Transport retries are bounded at 3, and the retry
classifier distinguishes a rolling rate limit (retry, honouring `Retry-After` up to 30 s)
from "this request can never fit" (fail immediately, with the provider's own words).

Measured on the shipped pipeline: **2 LLM calls of the 25 allowed**, largest single prompt
**2,161 tokens of 12,000**. That shows the accounting is wired up; it does not show the
limit binding under load, and it is stated that way.

### 6.2 Code-Graph RAG — the "we never send the whole app" claim, measured

`m4_genai/retrieval.py`. The retrieval substrate is M2's backward call-graph walk, which
already answers "which code can reach `sendTextMessage`". This module answers the next
question: *of everything that can, what do we put in front of the model?*

Ranking is by sink severity × lifecycle reachability × proximity to the sink. Unreachable
sinks are down-weighted by a factor of 0.35 — not to zero, because an unreachable
`DexClassLoader` still deserves a sentence, but never above a reachable one. Ties go to
the method **nearest the sink**, because the entrypoint three frames up is usually
`onCreate` delegating.

Caps: `MAX_CHAINS = 6`, `MAX_METHODS_PER_CHAIN = 3`, `MAX_STRINGS = 12`,
`DEFAULT_TOKEN_BUDGET = 1,800` for the workspace (lowered from 5,000 once the tool loop
was measured end to end — the pack is only round 0's cost; round 1 carries tool results
too). Selection is **pure and deterministic**: same `StaticReport` → same chains in the
same order, so a cached run and a live run are comparable and a regression is a diff
rather than a mood.

**Measured on 11 real MalwareBazaar-tagged banking trojans on the extractor VM**
(`data/measurements/rag_selection_ratio.json`) — the only place a corpus APK legally
lives:

|---|---|---:|---:|---:|---:|
| `d300e348` | Hydra | 48,449 | 8 | **0.017%** | 4,758 |
| `14b00535` | Ermac | 35,654 | 4 | 0.011% | 4,216 |
| `33ece839` | Coper | 16,044 | 8 | 0.050% | 4,786 |

entrypoint. The backward walk is not failing; it has nothing to walk.

### 6.3 The bounded tool loop

The model may call only six allowlisted, pydantic-validated, **read-only** tools:
`read_method`, `find_xrefs`, `method_strings`, `verify_transform`, `evidence`, `mitre`.
Every call is budgeted, bounded, and written to the ledger as an `AI_TOOL_CALL` node — so
the audit trail includes what the model asked for, not only what it concluded.

### 6.4 Prompt injection defence — structural, not textual

Three layers, each verified:

1. **The system prompt contains zero sample-derived tokens.** Verified on the decoy:
   2,279 characters, with no permission, component name or package leaked into it.
2. **All sample content arrives in the USER turn inside balanced `<untrusted_artifact>`
   blocks, XML-escaped.** Measured: zero raw `<`, zero unescaped `&`. A forged
   `</untrusted_artifact>` planted in a string constant is escaped to
   `&lt;/untrusted_artifact&gt;` and cannot terminate the block.
3. **The LLM never emits the score**, so an injected "output threat_score=0" changes
   nothing that reaches `S`. There is a test that feeds exactly that string and asserts
   `S` is unaffected.

Two further rules on the output side: LLM output that reaches a command surface is
validated (`validate_morph()` before anything touches adb or JS), and parameters are
injected as **JSON literals**, never string-concatenated into an expression — the same
discipline as SQL parameterisation, for the same reason.

### 6.5 The behavioural term `B` — weights are measured, not assigned

`B` is computed in Python from the enumerated booleans the model emits. The weight table
is 16 keys, and each weight is **the smoothed log-likelihood ratio**
`log(P(asserted|malware) / P(asserted|benign))` of the model's own assertions over 45
labelled corpus samples (21 malware / 24 benign), add-0.5 smoothed, capped at 2.0, and
clamped at 0. Derivation: `scripts/fit_behaviour_weights.py`.

| behaviour | weight | | behaviour | weight |
|---|---:|---|---|---:|
| `abuses_accessibility_service` | 1.74 | | `detects_analysis_environment` | 0.13 |
| `impersonates_a_known_brand` | 1.23 | | `hides_or_disables_its_own_icon` | 0.13 |
| `requests_device_admin` | 1.23 | | `intercepts_notifications` | 0.13 |
| `overlays_other_apps` | 0.67 | | `encrypts_data_before_sending` | 0.0 |
| `sends_sms_without_user_action` | 0.64 | | `gates_behaviour_on_installed_apps` | 0.0 |
| `exfiltrates_over_network` | 0.50 | | `harvests_device_identifiers` | 0.0 |
| `harvests_contacts_or_call_log` | 0.46 | | `loads_dex_at_runtime` | 0.0 |
| `monitors_clipboard` | 0.36 | | `reads_sms_content` | 0.0 |

**Why several weights are exactly zero, and why none is negative.** Measured signed LLRs
put `loads_dex_at_runtime` at **−1.09** (74% of benign apps assert it — split-APK and
dynamic-feature delivery) and `reads_sms_content` at **−1.06**. A negative weight on a
*model-asserted boolean* would hand the sample an injection channel: strings that goad
the model into asserting a benign-shaped behaviour would lower its own score. So a
non-discriminative behaviour contributes exactly nothing — the assertion is still
recorded, grounded and shown to the analyst, it just does not move `B`.

Exculpation is carried instead by `CONTEXT_WEIGHTS`, deliberately asymmetric in trust:

- **Deterministic static facts, computed in Python, the model never touches them:**
  `cert_signer_stable_years` −1.20 (measured LLR, signer key ≥ 730 days, not debug),
  `publisher_trusted` −2.00 (declared prior, never fired on the fit corpus),
  `lookalike_legitimate_privileged` −1.00 (prior),
  `targets_installed_financial_apps` +1.50 (measured LLR, capped),
  `debug_certificate` +1.23 (measured LLR). These carry the large exculpatory weights
  because the sample **cannot talk its way into them** — an old, stable signing key has
  to actually exist.
- **Two model-answered purpose questions**, at ±0.50 — deliberately small, because a
  model-asserted exculpatory boolean is an injection surface and small weight bounds the
  damage.

Combination: `B = sigmoid(B_BASE + Σ behaviour + Σ context)` with `B_BASE = −2.0`.
A key not in either table is **ignored**; a value that is not a real `bool` is **refused,
not coerced** (`"yes"`, `1` and `"true"` do not count); and if no positively-weighted
behaviour is asserted, `B` is exactly 0.0 — context alone never raises a risk claim out
of nothing.

Held-out quality, 10× stratified 5-fold CV with weights refitted inside every fold:
**B AUC 0.64, composite S AUC 0.86** on the 45 — against **0.47 / 0.57** for the previous
hand-weighted noisy-OR table, which ranked benign apps *above* malware.

### 6.6 The Verifier

Every claim the model makes must cite ledger nodes that resolve. Unresolvable citations
are dropped **per claim**, never all-or-nothing, so a partially-grounded response still
yields its grounded half. Verified live on the canary through a real provider:
`genai_static` in 7.6 s, 2 MITRE techniques mapped and grounded, **4 claims generated,
4 verified, 0 rejected** against 14 citable nodes.

## 7. M6 — The composite scorer

```
S    = 100 × min(1, 0.25·R + 0.50·F_AI + 0.15·G + 0.10·D)
C    = γ · (1 − |P_cal − B|),   γ = 0.4·has_static + 0.3·has_dynamic + 0.2·has_ml + 0.1·has_intel
```

`R` reputation, `F_AI` fused AI intelligence, `G` deterministic rule severity, `D`
static–dynamic drift. Every term is emitted as a `ScoreFactor` with its value, weight,
inputs and the ledger refs it rests on — which is what the UI's score-breakdown rail
renders, and why "nobody can explain the score on stage" is not a live risk.

Availability gating is explicit and unforgiving: a stub ML version, a `mock` GenAI
provider, a synthetic trace or an unavailable intel source do **not** count as evidence
and cannot inflate `S`, `γ` or `C`.

### 7.1 `F_AI` — from noisy-OR to log-odds, and why

Full derivation in `docs/FUSION_DERIVATION.md`. This is the single most consequential line
in the scorer — it decides half the composite — so the change was made against evidence,
not vibes.

**The original design** was noisy-OR: `F_AI = P_cal + B − P_cal·B`.

**The symptom, from two directions.** The official YouTube APK returned `S = 28 MEDIUM`,
with `F_AI` contributing 17.2 points on a `p_calibrated` of 0.344 against a *raw*
classifier probability of 0.008. And measuring each term separately over 60 labelled
samples through the real pipeline:

| term | malware mean | benign mean | lift | AUC |
|---|---:|---:|---:|---:|
| **S** (composite) | 55.733 | 47.633 | +8.100 | **0.636** |
| **P_cal** (ML alone) | 0.744 | 0.259 | +0.485 | **0.878** |
| **B** (GenAI) | 0.714 | 0.925 | **−0.210** | **0.473** |
| G | 0.697 | 0.543 | +0.153 | 0.704 |
| D, R | 0.000 | 0.000 | 0.000 | 0.500 |

**The composite ranked worse than the ML term it contains.** Every other layer was, in
aggregate, destroying signal the classifier had already found.

**Three causes, all fixed.**

1. *The questions asked about capability, not intent.* "Does it overlay other apps?" is
   answered yes by a video app doing picture-in-picture and by a banking trojan drawing a
   fake login. Measured: the model asserted **more** behaviours on benign apps (2.80) than
   on malware (2.43). Fixed by rephrasing the checklist around purpose and refitting the
   weights as measured LLRs (§6.5).
2. *`B` saturated.* `B = 1 − Π(1−wᵢ)` over weights all ≥ 0.40 reaches 0.97 at four
   assertions — **33 of 45 samples were above 0.95**, median 0.966. It was a step function
   on assertion count, not a risk gradient. Fixed by the sigmoid form.
3. *The structural one, in the fusion itself.* Noisy-OR is monotone increasing in `B`:
   `∂F_AI/∂B = 1 − P_cal ≥ 0`, so `F_AI ≥ P_cal` **always**. The behavioural layer could
   decline to add risk; it could never subtract it. The best it could do for a wrongly
   accused app was `B = 0`, returning the accusation unchanged. **Exoneration was
   arithmetically impossible** — which directly contradicts the product's stated purpose.

**What shipped:** log-odds evidence combination.

```
logit(F_AI) = logit(P_cal) + evidence
F_AI        = σ(logit(P_cal) + evidence)
```

The decisive argument is that this is not a new idea imposed on the system — it is the
form the quantities already have. `BEHAVIOUR_WEIGHTS` and `CONTEXT_WEIGHTS` *are* measured
log-likelihood ratios, and the textbook way to combine a prior with a likelihood ratio is
to add them in log-odds. The ML supplies the prior; the behavioural layer supplies the
likelihood ratio. Negative evidence is not a special case bolted on — it falls out.

Rejected alternatives, recorded so they are not re-proposed: demoting `B` out of the score
entirely (honest, but deletes the reason the system has a GenAI layer); a clamped signed
subtraction (arbitrary in probability space); a multiplicative discount (asymmetric for no
principled reason); and **conjunction scoring of the banking-trojan triad** — measured,
and it fired on **0 of 21 malware and 2 of 24 benign**, so it was not shipped.

Three properties held by test:
- **Silence is neutral.** `evidence == 0` returns `P_cal` exactly; a layer must not move
  the score merely by running.
- **`None` is not `0.0`.** A verdict predating the field falls back to noisy-OR, so old
  artefacts re-score identically rather than silently changing meaning.
- **`logit` is clamped** at 1e-6. The isotonic calibrator emits exact 0.0 and 1.0 at its
  flat ends; unclamped that is `NaN`, not merely wrong.

Measured effect on an app the classifier condemns at `p_cal = 0.80`, `G = 0.40`:

| behavioural layer says | F_AI | S | band |
|---|---:|---:|---|
| *(old noisy-OR, evidence absent)* | 0.980 | 55 | MEDIUM |
| nothing to say | 0.800 | 46 | MEDIUM |
| **trusted publisher, signer stable ≥ 2y** | **0.242** | **18** | **LOW** |
| targets banking packages | 0.972 | 55 | MEDIUM |

### 7.2 The composite an analyst actually sees

PR-AUC ranks; `S` is what lands in a queue. So triage claims are measured over `S`, by
**calling the shipped scorer** (`m6_score.engine.score`) over reconstructed reports —
never a local copy of the formula, which would agree today and drift silently after the
next weight change.

Configuration: **static + ML only** — no threat intel (`R = 0`, and a VT-derived feed
would be circular), no behavioural term (nothing detonated).

| | time-split test, n=481, 250 malware |
|---|---|
| reachable ceiling | **69** (computed from the shipped weights) |
| max `S` observed | 65 |
| **MEDIUM+ (S ≥ 40)** | **precision 0.9143, recall 0.7680** — 210 flagged, 192 TP, 18 FP |
| HIGH+ (S ≥ 65) | precision 1.0000, recall 0.0280 — over a **four-point** window |
| CRITICAL+ (S ≥ 85) | **structurally unreachable** in this configuration |

Read the ceiling and the table together. A precision of 1.00 over a four-point window is a
statement about the width of the window, not about the model. **The MEDIUM row is the one
that describes this configuration's triage behaviour**, and CRITICAL is reported as
unreachable rather than as an absence of critical samples.

A separate finding fell out of counting `S` and the *emitted band* separately: the band
histogram and the `S` histogram legitimately disagree, because the novelty escalator
promotes rows without moving `S`. Reporting only the band would charge 84 benign rows to
the score; reporting only `S` would hide them. Both are published.

| `MLPrediction.anomaly_escalate` | the ML layer, but see §5.7 | LOW→MEDIUM escalation | fires, does not move `S` |

## 8. The evidence ledger

SQLite (WAL) rather than Postgres + Celery + Redis: fewer moving parts, fewer 3 a.m.
failures.

**Canonicalisation** (`ledger/crypto.py`) exists so two machines compute the same hash for
the same node:
- floats rounded to 6 dp — `0.1 + 0.2` serialises as `0.30000000000000004` on one machine
  and can differ on another, which silently breaks chain verification;
- `-0.0` normalised to `0.0`;
- tuples become lists, because JSON has no tuple and a round-tripped node must still
  verify;
- `bool` checked **before** `int`, because `isinstance(True, int)` is True in Python and
  rounding a bool would turn it into `1`;
- sorted keys, no whitespace, unicode preserved.

**Chain + signature.** sha256 over the canonical form of everything except `node_hash` and
`signature`; genesis predecessor is 64 zeros; Ed25519 over the hash. A corrupt key file is
a **fatal, operator-level** error rather than an auto-regeneration, because regenerating
would leave every previously signed node unverifiable.

**Append-only in SQL, not just in Python.** `BEFORE UPDATE` and `BEFORE DELETE` triggers
`RAISE(ABORT, 'evidence ledger is append-only')`.

**Grounding enforced inside the write transaction.** `_assert_claim_is_grounded` refuses
an `AI_CLAIM` with empty or unresolvable `evidence_refs`, and `_assert_parents_exist`
refuses a dangling parent.

**Both properties are demonstrable live**, on a throwaway DB and key
(`make demo-reject`, `make demo-tamper`, `make demo-integrity`):
- *reject*: a claim citing nothing is refused; a **fabricated** citation is refused by
  resolution; the same claim is accepted once cited — and the refusals leave **no gap in
  the sequence numbers**, because grounding is checked inside the transaction.
- *tamper*: a two-layer result. The triggers refuse the `UPDATE` outright; after an
  attacker drops the triggers and rewrites the row, the hash chain still reports the break
  **at the exact seq**.

## 9. M3 — Dynamic analysis

### 9.1 Where it runs, and the rule

| Work | Runs on |
|---|---|
| Contracts, ledger, scorer, features, prompts, UI, all tests | laptop |
| M2 static over real corpus samples | GCE extractor VM |
| ML training / calibration / evaluation | GCE extractor VM, corpus from GCS |
| **Detonation of any real APK** | **GCE detonator VM, sealed VPC, Android emulator under KVM** |

**The rule, once:** a file under `data/samples/` or in the corpus bucket is never opened
by an installer, an emulator, or a `subprocess` on a developer machine. Static parsing
with androguard on the laptop is fine (it does not execute code); `adb install` on the
laptop is not.

GCP shape: dedicated project, two networks — `drishti-build` (has Cloud NAT, for image
building only) and `drishti-runtime` (**no NAT**, egress denied by default). The detonator
is `n2-standard-4` with `--enable-nested-virtualization`, no external IP, IAP tunnel only,
no SSH keys in the image. Tools are **baked into an immutable Packer image**, because the
runtime network cannot reach a mirror.

### 9.2 Containment is a test, not a claim

`verify_containment.py` runs before every detonation batch and its output is what the
signed attestation manifest commits to. Two corrections carried forward from v1, both
learned the hard way:

- **Do not use `nc -z`.** Android's toybox `nc` has no `-z` flag; it exits 1 with
  `Unknown option 'z'`, which made `blocked()` return True **unconditionally** — every
  containment check passed regardless of the real network state, and the signed manifest
  attested containment that had never been tested. Correct probe:
  `toybox nc -w N HOST PORT </dev/null` followed by an explicit `echo DRISHTI_RC=$?` that
  is parsed out of the output.
- **Fail closed.** `assert_probe_trustworthy()` runs a **negative control**
  (`127.0.0.1:1`, must read unreachable) and a **positive control** (a listener we
  started, must read reachable) before any verdict is trusted. `subprocess.TimeoutExpired`
  maps to rc 124 and reads as *blocked* — a blackhole `-j DROP` makes the probe hang past
  its deadline, and an unhandled timeout previously turned verification into a coin flip
  on DNS cache state.

A containment failure **aborts the batch**; it never downgrades to a warning. This is also
a standalone demo (`make demo-containment`): it accepts a sealed net and rejects the v1
`nc -z` probe.

Containment was proven **non-vacuous** on the first live detonation: the guest reached
8.8.8.8, 1.1.1.1 and the metadata server *before* lockdown, and none of them after.

### 9.3 Instrumentation

Frida **16.7.19** client + frida-server **16.7.19 android-x86_64**, versions matched
exactly, pinned `<17` because frida ≥17 imports `typing.NotRequired` (needs Python 3.11)
and the GCE image ships 3.10 — so `import frida` raises and the whole collector dies, not
just a version probe.

Hooks (`m3_dynamic/scripts/hooks.js`) are **observational only** and each emits
`(hook, technique, mitre, detail)`:

| Hook | Technique | MITRE |
|---|---|---|
| `PackageManager.getPackageInfo` / `getInstalledPackages` | software discovery | T1418 |
| `SmsManager.sendTextMessage` | SMS control | T1582 |
| `SmsMessage.getMessageBody` | capture SMS | T1412 |
| `DexClassLoader.$init` | download new code at runtime | T1407 |
| `Cipher.doFinal` | encrypted channel | T1521 |
| `URL.openConnection` | application-layer protocol | T1437 |
| `WindowManager.addView` | input capture via overlay | T1417 |
| `ClipboardManager.getPrimaryClip` | clipboard data | T1414 |
| `Runtime.exec` | command interpreter | T1623 |

**TLS interception is deliberately deferred, and that is stated as a choice rather than a
gap.** mitmproxy is in the image but never runs; `tls_intercepted` is never set true. The
`Cipher.doFinal` hook already yields plaintext *before* encryption, which is strictly
stronger — it also defeats custom crypto (T1521), which a TLS MITM does not.

Two emulator facts that cost hours and are now treated as given: `-writable-system` is
avoided on the critical path (with it, `adb remount` claims success while `/system` stays
read-only, and `adb reboot` can wedge the guest `offline` forever); and the emulator is
verified with `emulator -version`, **never `ldd`**, whose RPATH-resolved Qt libraries
produce false "not found".

### 9.4 Aggregation before the ledger or a prompt

One real sample called `Cipher.doFinal` **1,925 times in 60 s**. Appending a node per
event would have put 1,925 near-identical nodes in the ledger and blown the prompt budget.
Events are grouped by `(technique, mitre, hook)` with an occurrence count, capped at
`MAX_OBSERVATION_GROUPS = 40` — and `b_dynamic` is **provably unchanged** by aggregation.

### 9.5 Evasion detection — the module the whole narrative depends on

A sample that queries `PackageManager` for a banking app, does not find it, and quietly
stops looks — to any system that only counts observations — *exactly* like a clean app.
Both produce nothing.

The distinction is that **a clean app never asks**. So evasion is inferred from the shape
of what happened: **a probe, followed by silence**. `PROBE_TECHNIQUES` are the environment
*questions* rather than actions — T1418 (is the target bank installed?), T1426 (SIM,
build, emulator tells), T1430 (geo-gating) — and a run quieter than
`QUIET_EVENT_THRESHOLD = 12` events, with probes present, reads as stalling. Each pattern
names what the sample looked for, which is exactly what the frontier then synthesises.

The scoring consequence is enforced: **a sample that produced no observations is
`inconclusive`, never benign.**

### 9.6 What 115 live detonations actually produced

A 62-sample batch of MalwareBazaar family-tagged banking trojans (Coper, SpyNote, Hydra,
Ermac, Cerberus, BankBot, Alien, Hook, Octo, TeaBot, Joker) staged and detonated on the

| | |
|---|---|
| live detonations | **115** |
| completed with observations | **50** |
| total observations | **2,018** |
| runs with ≥ 3 events | 45 |
| failed | 63 — **26** `install_unsupported` (ARM-only ABI, the known x86 tooling limit), **35** `internal_error` (sample self-exited or crashed under Frida), **2** `install_failed` |

Family highlights: Joker 245 observations, Octo 39–51, BankBot up to 58, Ermac 26–31,

| Lifted | Count | Note |
|---|---:|---|

## 10. P5 — The frontier loop

### 10.1 JIT environment morphing

The evasion detector emits morph *proposals* ("the sample probed for an installed bank,
found none, and stalled; try `install_packages`"). `m3_dynamic/morph.py` is the applicator:
validate → render as a Frida config → apply on the running AVD → **diff pass-1 against
pass-2**, which is the flat-trace vs spiky-trace before/after the frontier claim rests on.

Two boundaries govern every line:
- **A morph changes what the sample OBSERVES, never what it can DO.** The rendered config
  feeds an observational hook that substitutes a synthetic return value; it never sends an
  SMS, writes a file, or grants a permission.
- **The LLM's morph params are untrusted input to a command surface.** `validate_morph()`
  runs before anything reaches adb or JS; params are injected as a JSON literal
  (`const MORPH_CONFIG = {...}`), never concatenated into an expression.

Caps: ≤ 20 packages (≤ 128 chars each), ≤ 200 SMS records (≤ 300 chars each), ≤ 100
contacts, ≤ 20 accounts. Five morph scripts ship: `build_props`, `sim_locale`,
`install_packages`, `clock_skew`, `files_present`. Content-provider kinds
(`sms_history`, `contacts`, `accounts`) are **deliberately unshipped** — an absent script
is *refused*, which is honest; a stub would claim a morph it did not apply.

The loop **closes**: wiring the call site alone was not enough, because nothing wrote
`EVASION_CHECK` nodes, so every proposed morph was silently dropped as ungrounded. A
morph's `derived_from` now resolves to a real evasion-check node.

**And the clean morph-then-wake capture is an honest negative.** Five real stall
candidates were morphed. Four AndroZoo quiet samples did not wake — two query their *own*
package (a repackaging/integrity check no environment morph addresses), two crash at Frida
instrumentation regardless. One BankBot sample *looked* like the money shot: pass-1
`failed` / 0 observations → pass-2 morphed `completed` / 4 observations (T1417 overlay,
T1418 package discovery). **A three-run unmorphed control refuted it** — the sample
completes with the same 4 observations unmorphed, so the pass-1 failure was a Frida
cold-start spawn flake, not evasion the morph unlocked. Claiming it would have been
dishonest; running the control is exactly why it is not claimed. What is missing is a
corpus sample with a genuine, checkable environment gate — the banking trojans available
mostly detonate passively already.

### 10.2 Generative C2 — with a provable inertness gate

Modern trojans phone home to a C2 that is dead, geo-fenced, or blocking the sandbox IP. A
normal sandbox captures the failed connection and stops, leaving the second stage
unanalysed. DRISHTI synthesises a schema-valid response so the sample proceeds.

Everything in the 717-line module exists to make one sentence true without qualification:
**a response DRISHTI serves to a sample is provably inert.** So the model is never trusted
to produce a safe response — it proposes *values* inside a fixed allowlist of response
shapes, and a deterministic, **fail-closed** gate (`assert_inert`) sanitises the result,
neutralises anything that could resolve to a live host / be executed / be loaded as code,
and records every change it made.

Three invariants, each pinned by a test:
1. **JSON control responses only.** Never a real APK, DEX, shellcode, ELF/PE/script, or a
   URL that resolves. Where a sample expects a binary payload, it gets a
   structurally-valid-but-functionless stub (an empty DEX header) — or the request is
   declined and the reason recorded.
2. **The shape is ours, not the model's.** It fills enumerated fields of a template we
   chose; it cannot introduce a new key whose value is a command verb.
3. **JSON-literal injection**, never string concatenation.

The synthesis and the inertness proof run and are tested without a network, a VM, or a
sample; only the thin mitmproxy addon is detonator-only.

## 11. M7 — Report, YARA, STIX, dossier

- **Report** (`report.html`): self-contained, no external assets, printable. The
  **Limitations section is derived** from provenance flags — partial analysers, replay vs
  live, hand-authored fixtures, unverified containment, rejected-claim count, mock
  provider, low confidence — never hardcoded. A sample that produced no runtime behaviour
  renders `INCONCLUSIVE, never benign`.
- **STIX 2.1**: ids are UUIDv5 over stable keys, so two exports of a job are
  byte-identical and the scorer's determinism is not undone one layer up. Publishes only
  **verified** claims and **observed** flows — never `synthesised` ones, which were served
  by our own Generative C2.
- **YARA**: keyed on repack-resistant artefacts; **the hash is metadata, never a
  condition** (pinned by `test_yara_rule_does_not_key_on_the_hash`). Below 3 distinctive
  strings it emits itself **disabled, with the reason**.
- **Dossier**: the package a cyber cell or bank fraud desk needs. `submission_is_manual`
  is **always True** — NCRP has no public submission API and nothing here files anything.
  The sample never leaves the analysis project.

Two defects found by *running* M7 rather than reading it: the YARA generator originally
keyed on the Kotlin reflection warning string, which ships in every Kotlin app — the rule
would have matched most of the Play Store (fixed with URL shape-checking and a
toolchain-boilerplate filter); and `str()` on an asn1crypto `Name` returns the object
repr, so a real run put `<asn1crypto.x509.Name 139086784924624 b'071\x16…>` into a
document intended for a fraud desk (now renders `CN=…, O=…, C=…`).

## 12. API and dashboard

FastAPI, in-process job runner, SSE for the live log stream. The route surface was frozen
at T0.6 and is pinned by `tests/contract/test_api_surface.py`:

`/api/health` · `/api/jobs` · `/api/jobs/{id}` · `/api/jobs/{id}/events` ·
`/api/jobs/{id}/{ingest,static,ml,genai,dynamic,score,verdict}` ·
`/api/jobs/{id}/report.html` · `/api/jobs/{id}/artifacts/{yara,stix,dossier}` ·
`/api/jobs/{id}/ledger[/verify|/export]` · `/api/evidence/{node_id}` ·
`/api/jobs/{id}/actions/{action}/confirm` · `/api/logs/stream`

Every consequential action (block, notify, push IOC) is a **proposal with a human confirm
button**, never auto-executed.

UI is Vite + React + TypeScript + Tailwind, eight views: Overview, **Code Graph**, Static,
AI, Reverse Engineering, Sandbox, Frontier, Ledger, Report. Notable properties:

- The dashboard's `Verdict` TypeScript is **generated** from the pydantic model
  (`ui/scripts/gen_verdict_types.py`); a contract test fails when it drifts.
- The **provenance badge reads the trace, not a config flag** — `STATIC_ONLY` draws as a
  red `NO TRACE`. Replaying a captured trace is legitimate and disclosed on screen;
  presenting it as live is not.
- Ungrounded score terms are labelled **"ungrounded — not measured"** rather than shown as
  a bare zero.
- The **Code Graph** view draws every edge from `StaticReport.call_paths`; nothing is
  inferred. Node fill encodes retrieval (hollow = no body ever recovered, therefore
  ungroundable by construction), and `nodesTouchedBy` attributes a tool call only through
  its validated arguments or a shared evidence ref — **never by fuzzy name match**.
- Layout is **pure and deterministic** (longest-path layering, fixed barycentre sweeps,
  stable tie-break, cycle-safe DFS marking feedback edges). A force simulation would settle
  differently per mount and make a graph screenshot unreproducible. 14 vitest cases cover
  it, because the only sample available on a developer machine is the canary, whose graph
  is two nodes on one path and exercises none of the layering.
- Fonts are **vendored, not linked** (217 KB of latin subsets) — a Google Fonts `<link>`
  would fall back to system sans on a projector with no network.

### 12.1 DRISHTI Shield — the on-device demo

An Android emulator on the demo laptop running `shield/` (Kotlin, minSdk 26, targetSdk 34,
zero dependencies beyond the framework), which intercepts a malicious APK **before** it
installs, in four layers: a pre-install `FileObserver` watcher + 250 ms sweep; a tap-time
intent filter; a `DevicePolicyManager` veto as device owner; and a post-install hash-match
failsafe.

Its test target is `canary/decoy-challan/` — an inert decoy named "RTO Challan" whose
manifest declares the Indian challan-fraud family's permission set while **every
implementation body is an empty method or a `Log.i`**. `verify_inert.sh` proves that by
comment-stripped grep and gates both the build and the demo bring-up. The paired
`canary/benign-sanchay/` declares the **identical five dual-use permissions** and is
cleared — which is the headline beat, because it is the answer to "do you just flag
everything?"

Measured, rehearsed cold eight times:

| Measurement | Value |
|---|---|
| cold start to ready | **31.5 s** |
| file landing → verdict, **cleared** app | 4411 / 4724 / 5320 / 5682 / 5696 ms |
| file landing → verdict, **blocked** app | 4368 / 4813 / 4878 / 5156 / 5519 ms |
| composite score arriving after the verdict | up to 33 s total |
| — of which M2 static | 4.9–9.7 s |
| — of which `genai_static` | 0.8 s cached, 35 s cold |
| — of which Shield itself | < 0.3 s |
| Layer 4 detection after install | < 1 s |

That rehearsal found **four silent failures** — each announced success and did something
else, the only failure mode that matters on stage. Most instructive: `adb install -r`
drops the *active admin* record while the *device owner* record survives, so
`dpm list-owners` kept reporting DeviceOwner while every `addUserRestriction` threw
`SecurityException`. Setup said "HELD"; the veto was dead. Fixed with
`dpm set-active-admin` each run plus a **self-test that engages the veto, reads the
restriction back from `UserManager`, and releases it** before the demo is handed over —
setup now dies if the veto cannot be proved.

### 12.2 End-to-end timing

- **Fast path: 2.95 s of local compute** (median of 3 runs × 3 samples), **94% of it M2
  static**. Everything else — ingest, 428-dim extraction, prompt assembly, the whole
  scorer — is under 80 ms combined. That is against the mock provider.
- Against the 17 real logged LLM calls (median **15.5 s**, range 6.8–58.7 s on a free-tier
  endpoint), the live fast path is **~18.5 s** — a *sum of two measurements*, and labelled
  as such rather than presented as one timing.

`make test` runs contract+unit (**1,232 passing** at `20a76cf`). `make e2e` runs the slow
ones (**15 passing**). CI runs contract tests on every push — those are the ones that
prevent the integration disaster. **CI never touches GCP and never sees a sample.**

The load-bearing contract tests are the parity ones. `test_feature_parity.py` is what makes
"one feature extractor for train and inference" a structural fact rather than a habit, and
`test_observation_ingest_parity.py` is its M3 analogue — it exists because the
`ObservationArtifact → DynamicTrace` conversion had been living inside a script, so the
offline fixture path and any future live path would have been two implementations of one
conversion.

Tests also caught real bugs that inspection did not: the cycle-handling defect in the
graph layout, a `StaticReport.lookalike` contract change that failed the vitest fixture at
build time rather than at runtime, and a detonator **protocol** bug — the first client sent
`detonate --sha256 X --morphs <json>` while the VM script takes `detonate <sha> [duration]`
positionally with morphs behind a *separate* subcommand. `test_detonator_client.py` now
asserts the command surface against `infra/gcp/detonator_run.sh` itself, which caught it
before it cost a VM start.

## 14. What is measured, what is designed, what failed

**Measured and working:**
- Time-split ML with bootstrapped intervals; isotonic calibration (ECE −83.6%)
- The composite over the shipped scorer: MEDIUM+ precision 0.9143 / recall 0.7680
- Code-Graph RAG selection: 4–9 methods from up to 48,449, ≥ 60% prompt-budget headroom
- 115 live detonations, 2,018 observations, containment proven non-vacuous
- Ledger chain verification, tamper detection at an exact seq, ungrounded-claim rejection
- Anti-injection posture: zero sample-derived tokens in the system prompt, all sample
  content escaped inside balanced untrusted blocks
- Sub-6-second on-device interception, rehearsed cold eight times

**Measured negative results, kept prominent because a negative result nobody can find is a
claim waiting to be made again by accident:**
- The **novelty escalator's lift is −0.0423** and it costs 84 benign LOW→HIGH promotions.
  Shipped only because it is an escalator that never moves `S`; it is not evidence.
- **"The certificate features work" is not supportable.** +0.0085 [0.0033, 0.0139], all of
  it `cert:validity_days`; two of the five columns are constant across every training row.
- **The lookalike discriminator does not discriminate** at the operating threshold
  (AUC 0.621, zero TROJAN_SHAPE verdicts either way) and is not a scoring signal.
- **Conjunction scoring of the banking-trojan triad** fired on 0 of 21 malware and 2 of 24
  benign; measured, then dropped.
- **The one morph-then-wake that looked like the money shot was refuted by its own
  control.**

**Designed, wired, not proven live:**
- `LiveSandboxSource` is implemented and unit-tested against a fake detonator, but no live
  detonation has been run *through the pipeline path* — the 115 runs were driven by hand.
  Until a `tests/lab/` run proves it, T4.9 is "wired and unit-tested", not "proven live".
- LLM self-repair from a tombstone (T4.3) is not built; snapshot restore is.
- TLS interception is deliberately deferred (see §9.3).
- `assess_icon()` has no caller in the pipeline, so icon impersonation is not in the
  scripted demo — and the VLM scored the same pixels 0.55–0.92 across five calls against a
  0.80 threshold, so **no fixed confidence may be quoted**.
- The fitted behaviour weights were measured against the *old* capability-phrased
  checklist. The prompt has since been rewritten to ask about purpose, so the held-out
  figures (B 0.644, S 0.871) **are not valid for the shipped configuration** until refit.

**Known limits that bound every number above:**
- The time-split test set holds **250 malware rows**; read the bootstrap intervals, not
  the point estimates.
- Recent-band labels come from MalwareBazaar while older-band labels come from AndroZoo's
  thresholded `vt_detection` — the two halves are not labelled by the same process.
- Composite `S` is measured in a static+ML-only configuration, so it cannot exceed 69 and
  cannot be compared against numbers from a run that had intel, a behavioural verdict, or
  a detonation available.
- Binary maliciousness only. The corpus carries no family labels that are not derived from
  `vt_detection`, so the multi-label panel is GenAI-derived and must be labelled that way.
